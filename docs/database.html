Database Implementation & Operations

CRANE uses PostgreSQL 16 as its single source of truth for all compliance data, audit logs, and configuration. This guide covers database design, backup strategies, scaling, and operational best practices.

Architecture Overview

CRANE's database stores:

  • Products & releases — all product registry data with version history
  • SBOMs & vulnerabilities — component manifests and CVE tracking
  • Risk assessments — STRIDE/TARA assessments, approvals, sign-off
  • Audit trail — immutable log of all user actions with timestamps
  • User accounts & RBAC — roles, permissions, team memberships
  • Configuration — deployment settings, policies, notification rules

All state is in the database. The backend is stateless and can be scaled horizontally without synchronization concerns.

Database Schema & Migrations

CRANE uses Alembic for schema versioning. Migrations are automatically applied on startup.

Automatic Migration on Startup

Every time the backend starts, it automatically runs pending migrations:

In start.sh
alembic upgrade head
exec uvicorn app.main:app --host 0.0.0.0 --port 8000

This means zero downtime for schema changes — just restart the backend and migrations apply automatically.

Custom Migrations

To add a custom migration (e.g., adding a new column, creating an index):

Terminal
cd backend
alembic revision --autogenerate -m "add_column_description"
# Edit alembic/versions/xxxx_add_column_description.py
alembic upgrade head  # test locally
git add alembic/versions/
git commit -m "chore(db): add column description"

Backup Strategy

Backups are critical. A database loss is a compliance disaster. Implement automated daily backups with off-site storage and test restoration regularly.

Daily Backup with pg_dump

Backup the entire database daily using PostgreSQL's native dump format:

Backup script (daily via cron)
#!/bin/bash
BACKUP_DIR="/backups/crane"
DATE=$(date +%Y-%m-%d_%H-%M-%S)
docker compose exec -T postgres pg_dump -U postgres cra_compliance | gzip > $BACKUP_DIR/crane-$DATE.sql.gz
# Keep 30 days of backups
find $BACKUP_DIR -mtime +30 -delete

Restore from Backup

To restore from a backup:

Terminal
# Stop the backend (but keep DB running)
docker compose down backend

# Restore the backup
gunzip < /backups/crane/crane-2026-06-02.sql.gz | docker compose exec -T postgres psql -U postgres cra_compliance

# Restart the backend
docker compose up -d backend

Performance Tuning

Indexes

CRANE automatically creates indexes on frequently queried columns (product IDs, timestamps, user IDs). For custom queries or high-volume deployments, add targeted indexes:

SQL
-- Create index on vulnerability CVE lookups (if slow)
CREATE INDEX idx_vulnerabilities_cve ON vulnerabilities(cve_id);

-- Create composite index for audit log range queries
CREATE INDEX idx_audit_log_user_created ON audit_log(user_id, created_at DESC);

Monitoring Slow Queries

Enable PostgreSQL slow query logging to identify bottlenecks:

Modify docker-compose.prod.yml
postgres:
  environment:
    POSTGRES_INIT_ARGS: "-c log_min_duration_statement=1000"  # Log queries >1 second

Then check logs:

Terminal
docker compose logs postgres | grep "duration:"

Scaling Considerations

Single-Instance (Most Deployments)

For organizations <500 users with <500 products, a single PostgreSQL instance is sufficient. Allocate:

  • RAM: 2-4 GB
  • Disk: 50-100 GB (depends on SBOM storage)
  • Connections: Default 100 is fine; CRANE backend uses connection pooling

High-Volume Deployments (>500 Products)

If scaling beyond single-instance:

  • Read replicas: Add PostgreSQL replicas for read-heavy workloads (reporting, dashboards)
  • Connection pooling: Use PgBouncer to multiplex connections from multiple backend instances
  • Partitioning: Partition the audit log table by date to keep query performance constant

Horizontal Scaling (Stateless Backend)

CRANE's backend is stateless. Scale by running multiple backend containers with the same database connection string:

docker-compose.prod.yml
backend:
  replicas: 3  # Run 3 backend instances, all sharing the same DB

Use a load balancer (nginx, Caddy, HAProxy) to distribute traffic.

Routine Maintenance

VACUUM and ANALYZE

PostgreSQL requires periodic maintenance to reclaim disk space and update statistics:

Weekly maintenance (add to cron)
docker compose exec -T postgres psql -U postgres cra_compliance -c "VACUUM ANALYZE;"

Monitor Disk Usage

Watch database size to plan storage capacity:

Terminal
docker compose exec postgres psql -U postgres cra_compliance -c "SELECT pg_size_pretty(pg_database_size('cra_compliance'));"

External PostgreSQL (Managed Services)

You can use a managed PostgreSQL service (AWS RDS, Google Cloud SQL, Azure Database, etc.) instead of the bundled container.

Configuration

In .env, set:

.env
BACKEND_DATABASE_URL=postgresql+psycopg://user:password@rds-instance.amazonaws.com:5432/cra_compliance
# Do NOT run the postgres container from docker-compose

Then omit the postgres service from docker-compose:

docker-compose.prod.yml (edit)
# Comment out the postgres service entirely
# postgres:
#   image: postgres:16-alpine
#   ...

Managed Service Considerations

  • Backups: Rely on your cloud provider's automated backups
  • Network: Ensure the database is in a private subnet, not publicly accessible
  • SSL/TLS: Most managed services enforce encrypted connections — configure the connection string accordingly
  • Cost: Managed databases are more expensive but reduce operational burden
