Configuration & Deployment

CRANE runs as a set of Docker Compose services configured entirely through a single .env file. This page covers the moving parts, the settings you should review before exposing an instance, and how to run isolated instances per client.

.env.example in the repository is the source of truth for available settings. Copy it to .env and adjust — the tables below describe the most important values.

The Docker Compose stack

A default install brings up the following services via docker compose up -d:

ServiceRoleDefault port
FrontendVue 3 application served by Vite5173
BackendFastAPI REST API8000
DatabasePostgreSQL 165432 (internal)

Common operations:

Terminal
# start / stop
docker compose up -d
docker compose down

# follow logs
docker compose logs -f backend

# apply updates
git pull && docker compose up -d --build

Environment variables

At minimum you must set a backend secret key and a database password. The installer generates these for you; for a manual install, set them yourself.

BACKEND_SECRET_KEY
Signing key for sessions/tokens. Minimum 32 characters. Generate with openssl rand -hex 32.
POSTGRES_PASSWORD
Password for the PostgreSQL instance. Use a strong, unique value.
POSTGRES_USER / DB
Database user and database name (defaults provided in .env.example).
Ports
Host ports for the frontend and API, if the defaults conflict with something already running.
Never commit your .env

It contains secrets. It is already covered by .gitignore — keep it that way, and rotate BACKEND_SECRET_KEY if it is ever exposed.

Vulnerability scanning (Trivy)

CRANE uses OSV and NVD data out of the box, with EPSS scores from FIRST.org for prioritisation. Trivy integration is optional and adds deeper component scanning. The first start downloads the vulnerability database, which is why it takes a few minutes.

LDAP & Active Directory

For enterprise environments, CRANE supports role-based access control backed by Active Directory or OpenLDAP. This lets you manage CRANE access through your existing directory rather than maintaining a separate user list. Configure the LDAP connection through the relevant environment variables in .env, then map directory groups to CRANE roles.

Keep at least one local admin account even with LDAP enabled, so you retain access if the directory becomes unreachable.

Production hardening

  • Change the default admin password on first login — before the instance is reachable by anyone else.
  • Terminate TLS at a reverse proxy (nginx, Caddy, Traefik) in front of CRANE; do not expose plain HTTP beyond localhost.
  • Restrict the database port — PostgreSQL should not be reachable from outside the Docker network.
  • Back up the database volume regularly (see below).
  • Keep CRANE updated — pull and rebuild to pick up fixes.

Backups & data export

All state lives in PostgreSQL. Back it up with a standard dump:

Terminal — backup
docker compose exec db pg_dump -U postgres crane > crane-backup.sql

Beyond raw database backups, CRANE offers full data export from within the application at any time — the basis of its "no vendor lock-in" promise.

Running multiple isolated instances

Consultants and managed-service providers typically run one CRANE instance per client. Because each instance is a self-contained Compose stack with its own database, isolation is the default — there is no shared tenancy to configure. To run several on one host:

  1. Use a separate directory per client

    Each gets its own .env, secrets and database volume.

  2. Assign distinct host ports

    So instances don't collide on 5173 / 8000.

  3. Export at project close

    Hand the client their complete dataset; tear the instance down cleanly.

Native multi-tenant support is on the roadmap; until then, separate instances are the recommended isolation model.

Reverse Proxy & TLS Setup

CRANE binds to localhost only by default. To expose it to the internet safely, run it behind a reverse proxy with TLS. This section covers two common approaches.

Option 1: Caddy (Recommended — Simplest)

Caddy automatically obtains and renews TLS certificates.

  1. Install Caddy

    Follow the Caddy installation guide for your OS.

  2. Create a Caddyfile

    Replace compliance.example.com with your domain:

    /etc/caddy/Caddyfile
    compliance.example.com {
  @frontend {
    not path /api/*
    not path /docs*
  }
  handle @frontend {
    reverse_proxy localhost:5173
  }
  handle /api/* {
    reverse_proxy localhost:8000
  }
}
  3. Run Caddy
    Terminal
    caddy run

    Caddy will automatically request a TLS certificate and listen on port 443.

Option 2: Nginx (More Control)

Nginx requires manual TLS setup but gives you more control.

  1. Install Nginx and Certbot
    Terminal — Ubuntu/Debian
    sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx
  2. Create Nginx configuration
    /etc/nginx/sites-available/crane
    # Redirect HTTP to HTTPS
server {
  listen 80;
  server_name compliance.example.com;
  return 301 https://$server_name$request_uri;
}

# HTTPS
server {
  listen 443 ssl http2;
  server_name compliance.example.com;

  location / {
    proxy_pass http://localhost:5173;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }

  location /api/ {
    proxy_pass http://localhost:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 300s;
  }
}
  3. Enable site and get TLS certificate
    Terminal
    sudo ln -s /etc/nginx/sites-available/crane /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl restart nginx
sudo certbot --nginx -d compliance.example.com

Upgrades & Maintenance

Keep CRANE updated to get security fixes and new features.

  1. Check for breaking changes

    Review the CHANGELOG.md for any migration steps.

  2. Pull latest code
    Terminal
    cd crane
git pull origin main
docker compose up -d --build
  3. Run database migrations
    Terminal
    docker compose exec backend alembic upgrade head

    Alembic only applies unapplied migrations, so it's safe to run repeatedly.

  4. Verify health
    Terminal
    docker compose ps
curl http://localhost:8000/api/v1/health

Rolling Back

If an upgrade breaks something, you can roll back to a previous version.

  1. Stop services
    Terminal
    docker compose down
  2. Checkout previous version
    Terminal
    git checkout v0.1.0  # or your previous version tag
  3. Start services
    Terminal
    docker compose up -d
  4. Optional: rollback database schema
    Terminal
    docker compose exec backend alembic downgrade -1

    Only needed if the previous version requires an older database schema.

Offline / Air-Gapped Installation

For environments without internet access, pre-pull Docker images and transfer them offline.

  1. On a machine with internet
    Terminal
    docker pull ghcr.io/cra-norm-engine/crane-backend:latest
docker pull ghcr.io/cra-norm-engine/crane-frontend:latest
docker pull postgres:16-alpine

docker save ghcr.io/cra-norm-engine/crane-backend:latest -o crane-backend.tar
docker save ghcr.io/cra-norm-engine/crane-frontend:latest -o crane-frontend.tar
docker save postgres:16-alpine -o postgres.tar
  2. Transfer tar files to offline machine

    Use USB drive, secure file transfer, or your preferred method.

  3. On the offline machine
    Terminal
    docker load -i crane-backend.tar
docker load -i crane-frontend.tar
docker load -i postgres.tar

docker images | grep crane
  4. Clone CRANE and run
    Terminal
    docker compose up -d
